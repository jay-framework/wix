# 58 - E.164 Participant Phones for wix-bookings

Status: [Implemented] (2026-11-16). Product decisions made (Option A, below); the user pre-approved proceeding to implementation once an independent reviewer judged this log development-ready (round 1 reviewer: development-ready, no blocking issues; its non-blocking suggestions were applied).

Builds on **DL #55** (wix validation parity; phone normalization phase **P1c**: `checkPhone`, `PhoneRules`, `PHONE_COUNTRY`, E.164 posting) and closes the bookings gap that DL #55 **Q20** left open because `createBooking` had not been probed. Paths are relative to `packages/` unless stated. jay is not touched. Line numbers are for branch `bookings-phone-format` at `8e543b0`.

## Decisions for the Implementer (TL;DR)

- **Product decision (settled, do not reopen): Option A, normalize.** A participant phone is parsed with the existing wix-forms phone machinery and sent to `createBooking` as **E.164**. A phone that cannot be parsed, or is invalid, gets a clear error in the browser and **no request is sent**.
- **One phone rule, reused.** The verdict and the posted value both come from `checkPhone` (`wix-forms/lib/utils/phone-normalization.ts:31`). Messages are the existing defaults: `PHONE` -> `'Please enter a valid phone number.'`, `PHONE_COUNTRY` -> `phoneCountryMessage` (`wix-forms/lib/utils/project-form-fields.ts:258-262`). No second regex, no new message text.
- **wix-forms changes (additive API):**
  1. `FormFieldSummaryView` (`wix-forms/lib/types.ts:53-58`) gains `phone?: PhoneRules`, the type `FormFieldView.phone` already uses (`types.ts:50`).
  2. `projectFormSummaryFields(fields, options?: ProjectionOptions)` sets `phone: { defaultCountry }` on `PHONE` fields when config `defaultPhoneCountry` is set. The service passes it (`wix-forms/lib/services/wix-forms-service.ts:76`), as it already does for `projectFormFields` (`:60-62`).
  3. `validateFormSummaryField`'s `PHONE` branch (`project-form-fields.ts:180-182`) uses `checkPhone(trimmed, field.phone)`.
  4. New exported `toPostedSummaryValues(fields, values)`: every `PHONE` value that `checkPhone` accepts becomes its `e164`; everything else passes through. It shares the per-value step with `toPostedValues`' `postedPhone` (`wix-forms/lib/components/submission-values.ts:187-192`). Exported from `index.ts` and `index.client.ts`.
- **wix-bookings changes:** `BookingFormFieldView` (`wix-bookings/lib/types.ts:23-28`) gains `phone?: PhoneRules`; `onSelectService` keeps `field.phone` in its mapping (`wix-bookings/lib/components/booking-flow.ts:220-227`); `onConfirmBooking` posts `toPostedSummaryValues(fields, formValues)` instead of `formValues` (`:285`).
- **No server-side normalization.** The `createBooking` action input (`wix-bookings/lib/actions/bookings-actions.ts:42`) is `Record<string, string>` without field types; the server would have to re-fetch the form summary to know which value is a phone. Out of scope (Q4).
- **Behaviour change (release note):** a local number without a country code (`054-123-4567`) used to pass the browser and fail with `UNKNOWN`; it now shows `'Please include the country code, starting with +.'` unless the site sets `defaultPhoneCountry`, in which case it is sent as E.164.
- **Error surface unchanged:** errors stay **form-level** (`bookingFailure === VALIDATION` + `bookingError` text, `booking-flow.ts:161-164`, `:264-271`). No per-field `errorRule` in bookings (Q5).
- **Bundle cost: zero.** libphonenumber-js is already inlined in wix-bookings' client through wix-forms' client (DL #55 Implementation Plan "Bundle cost"; Q6).
- **Agent feedback:** guide updates only (wix-bookings `agent-kit/plugin/wix-bookings-setup.md:119`, `wix-bookings-troubleshooting.md:58-60` currently say phones are sent as typed). No validation: there is nothing a page author can get wrong.

## Background

- **Booking form fields.** `onSelectService` calls `getFormSummary` (`booking-flow.ts:219`) and maps each field to `{ target, label, type, required }` (`:220-227`), dropping any other property. A service with no form uses `DEFAULT_PARTICIPANT_FIELDS` (`:42-46`): first name, last name, email — no phone.
- **Confirm.** `onConfirmBooking` (`:254-303`) reads raw input values (`readFormValues`, `:238-252`), validates each field with `validateFormSummaryField` (`:264-271`; first error -> `failBooking(VALIDATION, message)`, `:268`), then posts `formValues` unchanged (`:276-288`) to the `createBooking` action (`bookings-actions.ts:29-48`), which calls the service (`wix-bookings/lib/services/create-wix-bookings-service.ts:104-146`), which passes `formSubmission: input.formValues` (`:144`) to `createBookingRecord`.
- **Summary projection.** `getFormSummaryFields` (`wix-forms-service.ts:68-80`) projects with `projectFormSummaryFields` (`project-form-fields.ts:146-164`), keeping `STRING/EMAIL/PHONE/NUMBER/URL` fields. The Form Summary API returns no per-field country or allowed countries (`wix-forms/lib/wix-apis/get-form-summary.ts:5-13`), so the only phone rule available is config `defaultPhoneCountry` (`wix-forms/lib/config-loader.ts:29`, `:45`, `:58`).
- **Summary check today.** `validateFormSummaryField` (`project-form-fields.ts:166-187`) tests phones with `/^[+()\-\s\d]{7,}$/` only (`:180`). DL #55 left it untouched on purpose (Q20) and pinned it with a regression guard (`wix-forms/test/format-parity.test.ts:139-146`).
- **Forms' own phone path (DL #55 P1c).** `checkPhone` (`phone-normalization.ts:31-40`) returns `{ rule: NONE, e164 }` or `PHONE` / `PHONE_COUNTRY`. `toPostedValues` (`submission-values.ts:174-185`) maps tel values through `postedPhone` (`:187-192`). `defaultFieldMessage` (`project-form-fields.ts:231-256`) gives the default texts.

## Problem

Release QA (live probe) found that `createBooking` refuses spaced or dashed phones: a participant phone typed as `+1 202-555-0123` passes the browser regex, is posted as typed, and Wix answers HTTP 400. The visitor sees `bookingFailure === UNKNOWN` with no hint that the phone is the cause. Wix's visitor path accepts compact E.164 only — the same finding DL #55 P1c made for forms submissions — but bookings never received the fix because Q20 had not probed this path.

## Prior Art / Adjacent Mechanisms

- **DL #55 P1c** solved the identical problem for `wixForm`: one pure `checkPhone` gives the verdict and the E.164 value, so they cannot disagree. This log reuses it verbatim; the only new code is the summary-field adapter.
- **`ProjectionOptions`** (`project-form-fields.ts:81-85`) already carries `defaultPhoneCountry` into `projectFormFields`; the summary projection takes the same object.
- **`phoneRulesOf`** (`:131-144`) builds `PhoneRules` for full form fields; the summary has no field-level country, so only the config half applies.

## Q&A

**Q1 — Normalize or reject spaced phones? Answered (product): normalize (Option A).** Visitors type spaces and dashes; refusing them would be a regression in usability for a formatting detail.

**Q2 — A second phone rule for bookings? Answered (product): no.** `checkPhone` + existing messages; one rule across forms and bookings.

**Q3 — Where does `defaultCountry` come from?** Only config `defaultPhoneCountry`; the summary API has no field country (Background). `allowedCountries` is never set on summary fields, so `phoneCountryMessage` always yields the generic "include the country code" text.

**Q4 — Should the server normalize too? No.** The action has no field types; deriving them means another Wix call per booking. The browser is the only caller of the action in this plugin; a direct caller posting a bad phone still gets Wix's 400 (as today). Recorded as a known limit.

**Q5 — Is the bookings error per-field?** No, and this log does not change that. `failBooking` sets one `bookingFailure` + `bookingError` (`booking-flow.ts:161-164`); the message is the field's text, not prefixed with the label. The phone texts are self-explanatory ("phone number", "country code"), so form-level is acceptable. Per-field errors for bookings are a separate future item.

**Q6 — Bundle cost?** None new. wix-bookings' `vite.config.ts:38` externalizes only the exact `@jay-framework/wix-forms` string, and the client build inlines wix-forms' client, which since P1c carries libphonenumber-js (DL #55 "Bundle cost"). `validateFormSummaryField` calling `checkPhone` only makes that code reachable from bookings' own path. The implementer confirms by grepping the rebuilt `wix-bookings/dist/index.client.js` for `country_calling_codes` before and after (expected: present both times).

**Q7 — What does the store/input show after normalization?** The input keeps what the visitor typed; only the posted copy changes, as in forms.

**Q8 — Email/URL/number rules of `validateFormSummaryField`?** Unchanged; out of scope (no QA evidence).

## Design

### wix-forms

```ts
// types.ts
export interface FormFieldSummaryView {
  target: string;
  label: string;
  type: 'STRING' | 'EMAIL' | 'PHONE' | 'NUMBER' | 'URL';
  required: boolean;
  /** PHONE only: config `defaultPhoneCountry` (the summary API has no field country). */
  phone?: PhoneRules;
}

// project-form-fields.ts
export function projectFormSummaryFields(
  fields,
  options: ProjectionOptions = {},
): FormFieldSummaryView[];
// ...map adds: ...summaryPhoneRulesOf(type, options)  -> { phone: { defaultCountry } } | {}

// validateFormSummaryField, PHONE branch:
if (field.type === 'PHONE') {
  const phone = checkPhone(trimmed, field.phone);
  if (phone.rule === FieldRule.PHONE) return 'Please enter a valid phone number.';
  if (phone.rule === FieldRule.PHONE_COUNTRY)
    return phoneCountryMessage(field.phone?.allowedCountries);
}

// submission-values.ts
export function toPostedSummaryValues(
  fields: FormFieldSummaryView[],
  values: Record<string, string>,
): Record<string, string>; // PHONE values -> postedPhone(value, field.phone); others unchanged
```

- `postedPhone` changes its second parameter from `FormFieldView` to `PhoneRules | undefined` so both `toPostedValues` and `toPostedSummaryValues` call it; behaviour identical (trimmed empty stays empty, unaccepted value passes through unchanged — it is never posted because the browser check stops it first).
- The text for `PHONE` must come from a single source: implementer extracts the string used at `project-form-fields.ts:248` and `:181` into one module-level constant `INVALID_PHONE_MESSAGE` so the two cannot drift.
- `wix-forms-service.ts:76`: `projectFormSummaryFields(formSummary?.fields, { defaultPhoneCountry: config.defaultPhoneCountry })`.
- Export `toPostedSummaryValues` from `index.ts` and `index.client.ts` next to `validateFormSummaryField` (`index.ts:11`, `index.client.ts:10`); export type `PhoneRules` from `index.ts` and `index.client.ts`.

### wix-bookings

- `types.ts`: `BookingFormFieldView` gains `phone?: PhoneRules` (imported type from wix-forms).
- `booking-flow.ts:220-227`: add `...(field.phone ? { phone: field.phone } : {})`.
- `booking-flow.ts:285`: `formValues: toPostedSummaryValues(fields, formValues)`.
- Server, action and service unchanged.

## Trade-offs

- **Client-only normalization** keeps the action simple but leaves direct action callers on Wix's 400 (Q4).
- **Form-level error** remains; good enough for self-explanatory phone texts, worse for multi-phone forms (rare).
- **Local numbers now blocked without config** — stricter than before, but before they always failed at Wix anyway; the new error is actionable.
